## 2. issue-provision step by step

Workflow: [`.github/workflows/issue-provision.yml`](https://github.com/ravichandrapatel/gh-platform-control/blob/main/.github/workflows/issue-provision.yml).

Trigger: issue opened / edited / reopened / **labeled**. The label event is how a maintainer “starts” a public form that arrived unlabeled.

Order that matters:

```text
Authorize requester
    ↓
Validate pins + control config
    ↓
Parse issue body → request.json
    ↓
Validate against catalog + environments
    ↓
Render templates/<product>/ → stack files
    ↓
Mint GitHub App token (scoped to workload repo)
    ↓
Reject duplicate natural key (or attach same-issue)
    ↓
Open / refresh workload PR
    ↓
Create tracking Deployment issueops-<env>
    ↓
Comment + label status:pr-open
```

## 3. GitHub App vs GITHUB_TOKEN

| Token | Used for | Why |
| --- | --- | --- |
| `GITHUB_TOKEN` | Labels, comments, tracking Deployments on **control** | Same-repo automation |
| GitHub App installation token | Push branch + open PR on **infra-\*** | Cross-repo write; permissions Contents + Pull requests on workloads |

Mint step (pinned action SHA):

```yaml
- name: Mint GitHub App token
  id: app-token
  uses: actions/create-github-app-token@bcd2ba49218906704ab6c1aa796996da409d3eb1 # v3.2.0
  with:
    client-id: ${{ vars.CONTROL_CLIENT_ID }}
    private-key: ${{ secrets.CONTROL_APP_PRIVATE_KEY }}
    owner: ${{ github.repository_owner }}
    repositories: ${{ steps.validate.outputs.workload_repo }}
```

If the App lacks PR write on the workload, you get a confusing `status:provision-failed` after a green validate — I hit that while wiring App permissions.

**Tracking Deployments** on control use `issueops-dev` / `issueops-prod` — status only. They are **not** AWS apply gates. Real Environments (`dev` / `prod`) + OIDC live on `infra-*`.

## 4. Natural-key uniqueness

Key: `s3-bucket:<env>:<bucket_name>`.

| Edge | Behavior |
| --- | --- |
| Other open issue already claims key | **Fail** + attach both issues |
| Open workload PR already has stack | **Fail** + attach |
| Stack already on `main` | **Fail** + attach |
| Same issue re-run | **Attach / reuse** one PR |
| Failed issue (`validation-failed`, etc.) | Does **not** hold the claim |
| Same bucket name, different env | Allowed (different workload repo) |
| AWS orphan not in git | Non-goal for GitHub-only control |

## 5. Workload CI (tofu-pipeline)

On `infra-<env>`, PR CI calls the pinned composite/reusable pipeline from `gh-platform-actions`:

```text
validate → Checkov → plan (+ Conftest/OPA) → (merge) → Environment approval → apply
```

Control has a `status-sync` workflow that listens for `repository_dispatch` type `issueops_status` and flips labels (`status:plan-ok`, `status:applied`, …). The **contract is real**; the example `infra-dev` `tofu.yml` does **not** auto-fire that callback yet. Today labels often sit at `status:pr-open` until you wire the dispatch (or post it manually). Don’t read `status:applied` into the demo unless you’ve hooked that up.

I am **not** pasting a full module or teaching HCL here. The product catalog points at `s3/v1.0.0`. Platform engineers own that tag. IssueOps consumers fill a form.

## 7. Footguns

**Auto-labeling the form on a public repo.** Don’t. Drive-by provision is a real threat.

**Author not in `operators.yaml`.** Collaborator write is the other door — if neither, fail closed even with labels.

**App missing `pull_requests: write`.** Validate looks fine; PR step dies.

**Bare `dev` Environment on control.** Looks like “Ready to deploy to AWS.” Use `issueops-<env>` for tracking only.

**Floating action refs.** Pin SHA in `pins.yaml` and every workload `uses:`.

**Confusing control with apply.** Control never OIDC’s to AWS. If you “fix prod” from control, you designed it wrong.

**Natural key vs issue number.** Paths without issue suffix mean uniqueness is global per env — duplicates are a feature, not a bug.

**Assuming `status:applied` appears by magic.** `status-sync` exists on control; the starter workload `tofu.yml` does not post the callback yet. Wire it or dispatch manually.

## 8. FAQ

**Do I need Backstage for this?**  
No for this path. GitHub Issues are the portal. A K8s/Backstage IDP can sit beside it as a sibling (different control plane).

**Is this production-ready for strangers on the internet?**  
No. Public control is a **demo**. Harden operators, Interaction limits, private workloads, rotate App keys if leaked.

**Where do modules live?**  
`gh-platform-modules`, tagged. This series deliberately skips “how to write the module.”
