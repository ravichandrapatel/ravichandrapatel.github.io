[Part 1](/notes/vault-hub-architecture/) was the plan on paper — shared policy, identity metadata, one JWT mount per cluster with live OIDC instead of TokenReview. On paper it looked solid. Plans always do. This post is the lab run that either backs that plan up or shows where it falls over.

The setup is a hub and a spoke on kind under WSL2. No `lab-configure.sh` autopilot — every Vault command is typed out so failure modes stay visible. Tools for this run:

- kind, kubectl, Helm 3, Docker on WSL2
- Vault OSS **2.0.3** (Helm chart **0.34.0**)
- External Secrets Operator **v2.8.0** (chart **2.8.0**)

Scripts and manifests live under [`docs/vault-hub/`](https://github.com/ravichandrapatel/docs-and-adr/tree/main/docs/vault-hub). Root token and unseal keys stay in `.lab-secrets/` (gitignored) and are not pasted here. Shamir is lab-only. Demo values like `s3cret-demo` are fake.

### Quick recap of the Part 1 example

Part 1 carried one small example so the design stayed same:

- **OU:** `test1` (KV prefix `test1-ou`)
- **BUs:** `finance` and `retail`
- **Apps:** `payment-api` under finance, `oms` under retail
- **Env:** `prod`

Path shape is `{ou}-ou/{bu}/{app}/{env}` — for example `test1-ou/finance/payment-api/prod` and `test1-ou/retail/oms/prod`. Same Vault, same shared policy. Identity metadata is what tells them apart: **payment-api** reads its own secrets; a reach for **oms** should return 403.

Those names stay for the rest of this post.

## What i will build

<VaultK8sAuthFlow client:load />

The spoke gets a dedicated JWT mount at `auth/k8s-prod`. On real EKS, GKE, or AKS, `oidc_discovery_url` against the cluster issuer is enough. Kind has no public issuer the hub can reach, so a small JWKS publisher runs on the spoke and Vault is configured with `jwks_url` + `bound_issuer` instead.

Same verify path as cloud. Extra plumbing only because kind forces it.

The chain that has to hold: pod JWT → login on that mount → Identity Entity that already has metadata → shared policy expands → **payment-api** is allowed, **oms** is denied. If that lands, Part 1 was not just diagrams.

## Create the kind lab

`lab-up.sh` creates both kind clusters, installs Vault on the hub, unseals it, and drops the **payment-api** service account plus the JWKS publisher on the spoke. Hub shape: 1 control plane + **3** workers. Spoke: one node. The worker count matters.

**Issue-1:** A "normal" 3-node kind cluster is only 1 control plane + 2 workers, and the control plane is tainted. Vault anti-affinity wants three schedulable workers, so one Raft pod stays Pending forever. Three workers. Skip that and the lab never gets past install.

**Issue-2:** `too many open files` on kind nodes once Raft and kube-proxy get busy. Raise inotify before going further:

```bash
for n in $(kind get nodes --name vault-hub) $(kind get nodes --name vault-spoke); do
  docker exec "$n" sysctl -w fs.inotify.max_user_watches=524288
  docker exec "$n" sysctl -w fs.inotify.max_user_instances=1024
done
```

## Making JWKS reachable on kind

`lab-up.sh` script already applied the JWKS publisher resources, but the default `external_base` does not match this run's Docker IP. Vault hub should fetch signing keys over the kind network. `https://oidc.vault-spoke.lab` is a fake hostname and vault will fail to resolve the domain.

Update the jwks ConfigMap in the vault-system namespace in spoke cluster, so discovery deployment can advertises the base URL that vault hub can actually reach:

```bash
kubectl --context kind-vault-spoke -n vault-system create configmap oidc-jwks-config \
  --from-literal=issuer="${ISSUER}" \
  --from-literal=external_base="${OIDC_BASE}" \
  -o yaml --dry-run=client | kubectl --context kind-vault-spoke apply -f -
```

```text
configmap/oidc-jwks-config configured
```

Rollout restart the oidc-jwks so it reloads that ConfigMap:

```bash
kubectl --context kind-vault-spoke -n vault-system rollout restart deployment/oidc-jwks
```

```text
deployment.apps/oidc-jwks restarted
```

Wait until new replica pod is Ready before validating the health of the pod:

```bash
kubectl --context kind-vault-spoke -n vault-system rollout status deployment/oidc-jwks --timeout=120s
```

## Onboarding the spoke

We have configured the secrets, acl policy, entity metadata and JWKS is also reachable from the vault hub. Enable a JWT auth mount for this spoke cluster with path `auth/k8s-prod`:

```bash
kubectl --context kind-vault-hub -n vault exec vault-0 -- \
  env VAULT_TOKEN="$ROOT_TOKEN" vault auth enable -path=k8s-prod jwt
```

```text
Success! Enabled jwt auth method at: k8s-prod/
```

Kind still cannot use `oidc_discovery_url` cleanly — the issuer hostname is not reachable from the hub — so configure the mount with `jwks_url` and `bound_issuer`:

```bash
kubectl --context kind-vault-hub -n vault exec vault-0 -- \
  env VAULT_TOKEN="$ROOT_TOKEN" vault write auth/k8s-prod/config \
  jwks_url="${OIDC_BASE}/openid/v1/jwks" \
  bound_issuer="${ISSUER}"
```

```text
Success! Data written to: auth/k8s-prod/config
```

Create the JWT role for **payment-api**. `bound_subject` must match the Kubernetes service account. Projected tokens need `audience: vault`; miss that and Vault rejects the JWT in a way that looks like a JWKS failure when it is not:

```bash
kubectl --context kind-vault-hub -n vault exec vault-0 -- \
  env VAULT_TOKEN="$ROOT_TOKEN" vault write auth/k8s-prod/role/payment-api \
  role_type=jwt \
  user_claim=sub \
  bound_audiences=vault \
  bound_subject="system:serviceaccount:finance-prod:payment-api" \
  token_policies=universal-nested-policy \
  token_ttl=5m \
  token_max_ttl=10m
```

```text
Success! Data written to: auth/k8s-prod/role/payment-api
```

## Issues encountered during testing

1. **`vault-1` stuck Pending on the hub.** Vault uses pod anti-affinity, so three schedulable workers are required. A default 3-node kind cluster is only 1 control plane + 2 workers, and the control plane is tainted — one Raft pod never schedules. Use a **4-node** hub: 1 control plane + **3** workers.

2. **Raft join timeouts and kube-proxy CrashLoopBackOff.** Kind node file-watch limits were exhausted (`too many open files`). Raise `fs.inotify.max_user_watches` and `fs.inotify.max_user_instances` on every kind node before (or as soon as) the lab starts thrashing.

3. **ESO `connection refused` on port 32620.** That NodePort belonged to `vault-active`, which was the wrong Service to hit from the spoke. Use `svc/vault` NodePort **30820** instead.

4. **JWT validation errors.** The projected service-account token was missing `audience: vault`. The token audience must match the role auth role’s `bound_audiences`.

5. **403 on the exact KV path even with a “good” ACL.** The policy only granted `…/env/*`. `vault kv get …/prod` hits the leaf path with no child segment — grant the **exact** path **and** the `/*` path.

6. **Empty entity after first login.** Metadata was attached too late. Create the Identity Entity with metadata **before** the app’s first login, then bind the entity alias; otherwise login creates a hollow entity and the shared policy expands to nothing useful.

## Conclusions

We were able to deploy and validate what was discussed in Part 1.

**payment-api** logged in over JWT, read its own path, and got a flat 403 on **oms** — same Vault, same shared policy, different identity metadata. External Secrets used that same `auth/k8s-prod` role and synced a Kubernetes Secret without AppRole or a TokenReview service account. Per-cluster JWT with live JWKS worked on kind the hard way (`jwks_url` + `bound_issuer`); on cloud the publisher goes away and `oidc_discovery_url` takes its place.

What OSS still does not give for free: native DR, standbys that serve reads, or a real namespace boundary. Path + metadata + one shared template closes a lot of that gap — and still needs careful review, because one bad attribute or one bad HCL line hits every app under that OU/BU. Fine for a side project. Not the same as Enterprise.
