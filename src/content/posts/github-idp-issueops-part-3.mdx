## 0. Assumes

[Issue Forms & the public gate](/posts/github-idp-issueops-part-2/) is the human path. This post is **what the machine does** once the labels land — and why each stage exists.

I’ll walk it with the demo product: `issueops` + `product:s3-bucket` (S3 on AWS in my lab). Swap the product id and templates — or the cloud behind the modules — and the stages don’t grow a new personality. Control still never holds apply power.

By the time a PR opens, the rendered stack already has normal module `source`/`ref` lines for **what you already ship** — one modules monorepo or one-repo-per-module, AWS or not. Control fills templates; it doesn’t become your module factory ([modules library](/posts/github-idp-issueops-part-1/#44-gh-platform-modules--the-iac-library)). Good. I don’t want a second career writing everyone else’s modules.

## 1. issue-provision step by step

Workflow: [`.github/workflows/issue-provision.yml`](https://github.com/ravichandrapatel/gh-platform-control/blob/main/.github/workflows/issue-provision.yml).

Trigger: issue opened / edited / reopened / **labeled**. On a public form with empty labels, **labeled** is the real start gun — that’s when an operator chooses to run automation.

Order matters. Authz before App mint. Duplicate check before PR. Tracking Deployment after the PR exists.

```text
Authorize requester
    ↓
Validate pins + control config
    ↓
Parse issue body → request.json
    ↓
Validate against catalog + environments
    ↓
Render templates/<product>/ → stack files
    ↓
Mint GitHub App token (scoped to workload repo)
    ↓
Reject duplicate natural key (or attach same-issue)
    ↓
Open / refresh workload PR
    ↓
Create tracking Deployment issueops-<env>
    ↓
Comment + label status:pr-open
```

| Step | Tool | Why it’s there | Fail label (typical) |
| --- | --- | --- | --- |
| Authorize | `authorize_requester.py` | Fail closed on issue **author** | `status:validation-failed` |
| Validate config | `validate-pins.sh`, `validate-control.sh` | No floating pins / broken registry | `status:config-error` |
| Parse | `parse_issue.py` | Issue body headings → JSON | `status:validation-failed` |
| Validate request | `validate_request.py --product s3-bucket` | Catalog patterns + env exists | `status:validation-failed` |
| Render | `render_stack.py` | Templates + pins → stack files under `/tmp` | `status:validation-failed` |
| App token | `actions/create-github-app-token` | Cross-repo write without a human PAT | `status:config-error` |
| Duplicate | `check_duplicate_resource.py --attach` | Natural-key SoT in Git | `status:validation-failed` |
| PR | `open_workload_pr.sh` | Bot commit + `gh pr create` / attach | `status:provision-failed` |
| Tracking Deployment | `gh api …/deployments` | Status link on control (`issueops-<env>`) | `status:provision-failed` |

Successful run for [issue #15](https://github.com/ravichandrapatel/gh-platform-control/issues/15):

  repository: ravichandrapatel/gh-platform-actions

Catalog product pin for S3 is separate (`module.ref: s3/v1.0.0` in `config/catalog/products/s3-bucket.yaml`). How to bump pins safely: [bump pins](/posts/github-idp-issueops-part-4/#8-extend--pins-products-envs).

## 2. GitHub App vs GITHUB_TOKEN

| Credential | Where | Purpose |
| --- | --- | --- |
| `GITHUB_TOKEN` | Control job | Labels, comments, tracking Deployments, collaborator authz API |
| GitHub App (`CONTROL_CLIENT_ID` + `CONTROL_APP_PRIVATE_KEY`) | **Control** repo only | Cross-repo Contents + Pull requests write on `infra-*` |
| `MODULES_GIT_TOKEN` | **Workload** repo | `contents:read` on modules during `tofu init` |
| Cloud OIDC (demo: AWS) | Workload only | Plan/apply — never on control |

Mint step (pinned action SHA):

```yaml
- name: Mint GitHub App token
  id: app-token
  uses: actions/create-github-app-token@bcd2ba49218906704ab6c1aa796996da409d3eb1 # v3.2.0
  with:
    client-id: ${{ vars.CONTROL_CLIENT_ID }}
    private-key: ${{ secrets.CONTROL_APP_PRIVATE_KEY }}
    owner: ${{ github.repository_owner }}
    repositories: ${{ steps.validate.outputs.workload_repo }}
```

**Copy/paste class:** Requires modification — pin the action SHA you trust; never put `CONTROL_*` on `infra-*`.

Footgun I hit: App with Contents write but **without** Pull requests write → branch pushes, `gh pr create` fails → `status:provision-failed` after a green validate.

How to create the App and set secrets: [stand-up & harden](/posts/github-idp-issueops-part-4/#3-github-app--create-install-credentials).

**Tracking Deployments** use `issueops-dev` / `issueops-prod` — status only. Real Environments + OIDC live on `infra-*` ([Issue Forms & the public gate](/posts/github-idp-issueops-part-2/#6-tracking-vs-deploy-environments)).

## 3. Natural-key uniqueness

Key: `s3-bucket:<env>:<bucket_name>`.

Scan order: control issues with claim labels → open workload PRs → `main`.

| Edge | Behavior |
| --- | --- |
| Other open issue already claims key | **Fail** + attach both issues |
| Open workload PR already has stack | **Fail** + attach |
| Stack already on `main` | **Fail** + attach |
| Same issue re-run | **Attach / reuse** one PR |
| Failed issue (`validation-failed`, etc.) | Does **not** hold the claim |
| Same bucket name, different env | Allowed (different workload repo) |
| AWS orphan not in git | Non-goal for GitHub-only control |

## 4. Workload CI (tofu-pipeline)

Control stops at “PR open.” Everything that touches the cloud runs on the **workload** via the pinned reusable workflow in `gh-platform-actions`.

Caller pattern (starter: [examples/infra-dev/.github/workflows/tofu.yml](https://github.com/ravichandrapatel/gh-platform-control/blob/main/examples/infra-dev/.github/workflows/tofu.yml)):

- Detect which `stacks/**` dirs changed  
- **PR:** `command: plan` → `tofu-pipeline.yml@<same SHA as pins.yaml>`  
- **Push main:** `command: apply` + `confirm_apply: APPLY`  
- Pass `MODULES_GIT_TOKEN` so `tofu init` can fetch your private (or rate-limited) modules repo  
- Permissions: `contents: read`, `id-token: write` (OIDC), `actions: write` (plan artifact between jobs)

Why multi-stage? So **plan never waits on Environment approval**. Old single-job pins make “plan” look stuck behind prod reviewers. Current shape:

```text
validate → Checkov → plan (+ Conftest) → (merge) → Environment approval → apply
```

| Job | What runs | Environment gate? |
| --- | --- | --- |
| `validate` | `tofu fmt -check`, `init -backend=false`, `validate`, Checkov | No |
| `plan` | OIDC → full `init` → `plan` → Conftest/OPA on `tfplan.json` → artifact | No |
| `apply` | Download that plan → `apply` | **Yes** (`dev` / `prod` on workload) |

Defaults (checksum-pinned in the workflow): OpenTofu `1.10.10`, Conftest `0.68.2`. Policies live under `gh-platform-actions/policies/conftest/terraform/` (including `s3.rego`).

### What the PR actually contains

Rendered from `templates/s3-bucket/` — a thin root that **calls modules you already version**:

- Backend stub `s3 {}` + `backend.hcl` skeleton for that account’s state  
- `module` blocks with `source = "git::…"` — in my demo that’s `gh-platform-modules.git//s3?ref=s3/v…` (and tagging the same way); if you release `ORG/terraform-aws-s3` at `v1.2.0`, the template points there instead  
- Product defaults (encryption on, public access block all true)  
- Outputs `bucket_id` / `bucket_arn`  
- Header comment linking back to the control issue  

So the IssueOps PR is wiring + refs + product defaults — not a rewrite of your module on every request.

## 5. status-sync

Control has [`status-sync.yml`](https://github.com/ravichandrapatel/gh-platform-control/blob/main/.github/workflows/status-sync.yml): `repository_dispatch` type `issueops_status` with payload states `plan_ok` | `plan_failed` | `applied` | `apply_failed`.

I have the callback contract on control. The starter `infra-dev` `tofu.yml` doesn’t post it yet, so labels often sit at `status:pr-open` until you wire the dispatch (or fire one by hand). Sample payload shape is in the workload example README if you want to hook it up.

## 7. Footguns

These are **path** footguns (operating the machine). Bootstrap mistakes are in [stand-up & harden](/posts/github-idp-issueops-part-4/).

**App missing `pull_requests: write`.** Validate looks fine; PR step dies.

**App secrets on the wrong repo.** `CONTROL_*` must be on **control**, not on `infra-*`.

**Bare `dev` Environment on control.** Looks like a deploy Environment. Use `issueops-<env>` for tracking only.

**Floating action refs.** Pin SHA in `pins.yaml` and every workload `uses:`.

**Confusing control with apply.** Control never OIDC’s to the cloud.

**Natural key vs issue number.** Paths without issue suffix mean uniqueness is global per env — duplicates are a feature.

**Assuming `status:applied` appears by magic.** Wire `status-sync` or dispatch manually.

**Missing `MODULES_GIT_TOKEN` on workload.** Validate/init can’t read private modules.

**Old single-job pipeline pin.** Plan waits on Environment — bump to multi-stage SHA.

**Duplicate claim left open (`status:pr-open`).** Blocks new requests for that key.
