Recently I started building an internal developer portal as a side project. When I got to architecture and tool selection, one question kept coming up that I couldn't skip past: what lives where, and who gets to access it. Before I touched implementation, I needed to answer that everything else in the architecture would end up built around it.

Going back through everything an internal developer portal actually does, the thing I kept landing on first was secrets. Whether the portal ends up single-tenant, multi-tenant, multi-account, or multi-cloud, none of that matters if I haven't figured out how to store secrets securely underneath it. This post is my journey into finding the right answer for my own use case, not a general one.

## The Tool That Checked Every Box Except the Budget

I looked at a lot of options for storing secrets securely. AWS Secrets Manager was the obvious first stop — easy to use, easy to integrate, secure by default. Azure Key Vault and GCP Secret Manager were both fine candidates too. But I kept coming back to one problem: I need something with no cloud lock-in, so I can bootstrap this IdP on any cloud without rebuilding the secrets layer later.

That one constraint did most of the filtering by itself. No cloud lock-in, works on VMs or containers, can hand secrets to both, supports OIDC-based auth for cloud workloads, gives me real isolation between tenants, and has an HA/DR story I can trust. That's a short list to write down, but it ruled out almost everything except one tool.

**HashiCorp Vault**. I've been running **Vault Enterprise** at work for the past five years, and it checks every one of those boxes without me having to think twice. There's just one problem: this is a side project, and I don't have an Enterprise budget for it. So my eyes landed on Vault OSS instead and I already knew going to **Vault OSS** doesn't give you namespace isolation or the HA story Enterprise does. Those are the things you pay for.

That's the actual fork I was standing at: Enterprise has the isolation model I trust, OSS doesn't, and I can't afford Enterprise. So the rest of this post is me finding out how much of that gap I can actually close on my own and where I hit the point OSS just can't get me there.


To make this concrete, I'll carry one example through the rest of this post instead of talking in the abstract about "apps" and "tenants."

Picture the org as it'll actually look once this is live: a top-level org (I'll call it test1), with business units underneath it say, **finance** and **retail** and each BU running its own apps. Finance runs something called **payment-api**. Retail runs something called **oms**. Same Vault, same org, two completely different teams who should never see each other's secrets.

If this design works, **payment-api** should read its own secrets without a second thought, and get flatly denied the moment it reaches for anything under retail's **oms** same policy engine, same Vault instance, nothing but identity telling them apart.

## Testing the Obvious Thing First

I started with the initial design for app level isolation, I will use AppRole with ACL policy for each app, so will have 1 policy and role for **payment-api** and 1 policy and AppRole for **oms**. In theory when one app tries to read another app's secret it should get 403 access denied error.

On paper it looks good, but doing this for two apps I can manage it, what if I need to onboard multiple applications and multiple organizations, then entire day goes into writing the policy.hcl files for each and I need to spend a night trying to fix the issues, where and what is causing the issue. This idea is good when you have a handful of applications and is not the correct architecture path.

It resolves the policy sprawl we get from using a single policy per app — instead, I should create one shared policy template, used by any secrets path, driven by identity entity metadata.

Why identity entity metadata wins. Without metadata-driven policies, every new application becomes another policy lifecycle to own, review, version, and test. Using identity entity metadata moves onboarding from writing HCL to assigning attributes. The policy ACL stays as a single shared template. So taking my earlier example into consideration, the identity entity carries `<OU>/<BU>/<APP_NAME>/<ENV>`.

Example: For **payment-api**, that's test1/finance/payment-api/prod, and for **oms** it's the same shape, test1/retail/oms/prod, just with different values. Same policy template, different metadata, different result.

Below is what I finalized for the shared policy template. Prefix naming is `{ou}-ou`, then `{bu}/{app_name}/{env}` (plus `{bu}/shared/{env}`). Platform owns new OU/BU prefixes; app teams don't invent paths in PRs without that review.

**shared/** is BU-wide on purpose, not cross-tenant. Platform jobs that span BUs need their own entity/policy, not a wider universal template.

You need the exact path and the /* path. vault kv get hits the exact path; nested keys need the wildcard. Skip Issues Encountered and you'll paste a 403 into prod. Metadata-driven policies still need careful review. A bad template is a cross-tenant leak or a silent 403 with nice syntax.

```hcl
# Exact path: what `vault kv get .../prod` hits (without this: 403)
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
# Nested keys under that path
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
# Intentional: every app in the same BU can read that BU's shared/ path
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
# Self-lookup / debugging; not general app business logic
path "identity/entity/id/{{identity.entity.id}}" {
  capabilities = ["read"]
}
```
