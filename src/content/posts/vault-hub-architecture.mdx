I don’t want a Vault per team.

One broker on the hub. Spokes authenticate in. Secrets sit on paths that identity already decided. That’s the shape I’ve been running toward in `idp-gitops-bridge` — runbooks and Helm overlays live under `docs/adr/vault/` if you need the full write-up later. These are the notes I wish I’d had on day one.

## Why a hub

Per-tenant Vault looks tidy on a whiteboard. In production it’s seal keys, Raft disks, audit devices, backup jobs, upgrade weekends — multiplied by every OU that thinks it’s special.

So:

1. One **Vault Hub** (OSS unless you buy Enterprise).
2. Multi-tenancy in OSS = **path convention + policies**. Namespaces and native DR replication are Enterprise — label them, don’t pretend.
3. Hub–spoke GitOps already splits “hub bootstraps, spoke owns day-2.” Vault fits the same mental model: central security broker, not a pet per cluster.

![Hub topology — clusters auth in; IdP for humans; short-lived creds out](/posts/vault-hub/architecture.png)

## Principles that actually stuck

**Identity-first.** After login you’re an Identity Entity with metadata. Not a floating token with a handwritten policy name.

**Policy minimalism.** One universal template. Not two hundred `payment-api-prod.hcl` files rotting in git.

**No static cloud/cluster master keys in the workloads.** Auto-unseal via cloud KMS. Machines via JWT / Kubernetes auth or a carefully bounded AppRole. Humans via OIDC (Azure AD, Okta — pick your IdP).

## Path shape

| Metadata | Example |
| --- | --- |
| `ou` | `test1` |
| `bu` | `finance` |
| `app_name` | `payment-api` |
| `env` | `prod` |
| `cluster` | `eks-cluster-101` (set at onboarding, not by the pod) |

```text
{{ou}}-ou/data/{{bu}}/{{app_name}}/{{env}}/*
```

Finance payment-api prod → `test1-ou/data/finance/payment-api/prod/...`. Retail OMS is another leaf. Same mount. Different metadata. Deny by construction.

KV v2 on every `*-ou` mount.

## Universal policy

```hcl
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
path "identity/entity/id/{{identity.entity.id}}" {
  capabilities = ["read"]
}
```

Exact leaf **and** `/*`. That matters — see the footgun below.

Hub operators: auth mounts, entity *aliases*, KV *metadata*. Not tenant secret data. If SREs can rewrite `identity/entity/*` metadata, they can impersonate any app.

## Machine auth — two doors

Don’t create `auth/k8s-<every-cluster-uuid>`. Group by trust domain: `k8s-prod`, `k8s-nonprod`, `k8s-platform`. Bind `iss` + `sub` on the role. Same app on EKS and AKS = two roles under `k8s-prod`, different issuers.

Toggle these. Watch the trust boundary move.

Native K8s / JWT is the cleaner machine story. AppRole with no SecretID shows up in the runbook as an option; some reviews call it single-factor. On kind I used AppRole + secret_id — faking a cluster OIDC issuer wasn’t worth it for a local proof.

## HA / audit / DR (boring, required)

Raft ×3 (×5 if you care). Dual disks: data + audit. Cloud KMS auto-unseal. LB only routes `/sys/health` **200** (active leader). OSS standbys forward; they don’t serve reads.

Audit on immediately after init. Two devices, different types. Vault stops taking traffic if it can’t write audit.

OSS DR = Raft snapshots to object storage + restore automation. Warm standby replication is Enterprise.

### ACL footgun

Policy with only `.../{{env}}/*` grants `.../prod/*`. Exact leaf `.../prod` (what `vault kv get` hits) was **deny**. Capabilities on `.../prod/db_password` were fine.

Grant the exact leaf, or use a trailing `*` on the leaf segment. I learned that on this lab.

Also: stamp Identity Entity metadata **before** first login. Empty entity + later “alias already exists” is a miserable afternoon.
