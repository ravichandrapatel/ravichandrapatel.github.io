## 1. Intro and Issue

I am currently working on building my own internal developer portal. While debating the architecture I hit a familiar question: where do secrets live?

What I am creating here is a **central Vault Hub** for that portal — one broker shared by the control plane and application teams, running on **Vault OSS**, with multi-tenant isolation that does not depend on Enterprise namespaces. The design question is simple: can one app read only its own secrets, and get a hard deny everywhere else, without me writing a new policy file for every onboarding?

I went through a lot of documentation and blogs and eventually narrowed it to Vault. I have been using Vault Enterprise across multiple projects for the past five years, so I want to pull those same principles into this portal setup. I do not have the budget for an Enterprise license right now, so I am on Vault OSS. Namespaces, native DR replication, and performance standbys that serve reads are missing. Some of that I can approximate. Some of it I cannot. That is fine — I still want the operational shape I am used to.

Went back to the drawing board. During research one gap stood out: almost nobody writes clearly about **how to kill policy sprawl** when you are stuck on OSS and still need multi-tenant isolation.

Let’s take an example of an enterprise layout and stick with it for the rest of this note — lab, UI, and later when real clusters come online:

| Piece | Example |
| --- | --- |
| Org / OU | `test1` |
| Business unit (app owner) | `finance` |
| Application | `payment-api` in `prod` |
| Neighbor business unit | `retail` |
| Neighbor application | `oms` in `prod` |

`finance` / `payment-api` should read its own path. The same identity must get **403** on `retail` / `oms`. Same Vault, same mount family (`test1-ou/`), different identity metadata. If that cross-read ever succeeds, the design failed.

From here the note follows one path: decision, how I proved it on kind, what broke, and what I would trade off again.

## 2. Architecture and Decision

For the portal I do not want a Vault per team. I need a **central Vault** where the control plane lives. Application teams, other clusters, and VMs authenticate into that same broker.

I am selecting a **three-node** Vault for real environments. Raft leader election wants an **odd** quorum (same idea as etcd). Three is the minimum I will call HA. Five later if the platform gets serious. On OSS, multi-tenant isolation is **path convention + policies**. Namespaces and native DR stay Enterprise — I label that honestly.

![Hub topology — clusters auth in; identity provider for humans; short-lived creds out](/posts/vault-hub/architecture.png)

Three principles drive the rest of the design:

1. **Identity first** — login lands on an Identity Entity with metadata.
2. **Policy minimalism** — one universal policy template driven by that metadata.
3. **Zero static credentials** in the workloads — short-lived machine auth, cloud KMS auto-unseal in real clusters, humans on OIDC.

For the enterprise example above, the identity stamp on `payment-api` looks like this:

| Metadata | Example | Notes |
| --- | --- | --- |
| `ou` | `test1` | top-level mount prefix |
| `bu` | `finance` | business unit folder |
| `app_name` | `payment-api` | application id |
| `env` | `prod` | lifecycle |
| `cluster` | `eks-cluster-101` | set at onboarding — not by the pod |

```text
{{ou}}-ou/data/{{bu}}/{{app_name}}/{{env}}/*
```

That resolves to:

- Allowed: `test1-ou/data/finance/payment-api/prod/...`
- Denied for that same identity: `test1-ou/data/retail/oms/prod/...`

The universal policy is one file for every app. Exact leaf **and** `/*` are both required (see Issues Encountered).

```hcl
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
path "identity/entity/id/{{identity.entity.id}}" {
  capabilities = ["read"]
}
```

Create the entity **with metadata before** the first login.

I am not creating one auth mount per cluster. I group by trust domain: `k8s-prod`, `k8s-nonprod`, `k8s-platform`. Roles bind `iss` (cluster issuer) and `sub` (namespace:SA). Toggle Native K8s vs AppRole below — the arrows are the trust boundary.

## 4. Issues Encountered

**Exact leaf vs `/*`.** A policy that only ends in `.../{{env}}/*` grants under `.../prod/`. The exact leaf `.../prod` (what `vault kv get` hits) came back **403**. Capabilities on `.../prod/db_password` were fine. Fix: grant the exact leaf path as well (or trailing `*` on the leaf). That is why the universal policy has both stanzas.

**Bootstrap order.** If the workload logs in before the Identity Entity has metadata, you get a ghost entity and later “alias already exists” fights with Terraform. Stamp entity + metadata + alias first.

**Root token in the UI.** Works for kind. The UI itself warns that the root token is not stored in the browser. Never use this pattern on a shared cluster.

**Docker socket on WSL.** `kind create` failed until `DOCKER_HOST=unix:///var/run/docker.sock` pointed at the real Docker engine instead of a broken containerd endpoint.

**Port-forward flakiness.** CLI against `127.0.0.1:8200` died when the forward dropped. Running `vault` via `kubectl -n vault exec vault-0 -- ...` was more reliable for the lab script.

**OSS feature honesty.** I kept catching myself writing as if namespaces or warm-standby DR existed. They do not on OSS. Path + policy is the tenancy story until a license changes the rules.

## 5. Pros and Cons

| | Pros | Cons |
| --- | --- | --- |
| **Central Vault Hub** | One seal/backup/upgrade story; teams share a broker | Hub is a shared dependency — plan snapshots and restore |
| **OSS + path tenancy** | No Enterprise license to start; metadata-driven isolation works | No namespaces; no native DR; OSS standbys do not serve reads |
| **Universal policy** | Kills per-app policy files; onboarding is metadata + alias | Templating bugs (exact leaf) are easy to miss; bootstrap order matters |
| **Trust-domain auth mounts** | Few mounts (`k8s-prod` / `nonprod` / `platform`) | Role design must bind `iss`/`sub` carefully |
| **kind + Helm dev mode** | Fast proof of allow/deny and UI | `inmem`, no HA — must not confuse with the Raft values above |
| **AppRole in the lab** | Easy without cluster OIDC | Weaker story than native K8s JWT for real workloads |

## 6. Conclusions

What I set out to create is a **Vault Hub for my internal developer portal**: one OSS broker, tenants isolated by metadata, one universal policy. I will keep using the same enterprise example — `finance` / `payment-api` allowed, `retail` / `oms` denied — when I move from kind to Raft and when I swap AppRole for real Kubernetes JWT auth.

I am staying with that Hub model and a **three-node Raft** shape for anything past the lab. Kind + Helm **dev** mode was enough to prove allow and deny, and to walk the UI. The production values above are what I want next — TLS, dual disks, audit job, snapshot CronJob — once cloud KMS unseal and real storage classes are wired.

Policy sprawl was the research gap that started this. The lab answered it without a graveyard of `app-env.hcl` files.

Next for me: trust-domain JWT against a real spoke OIDC issuer (still as `payment-api`), External Secrets / VSO on the universal path, and one Raft snapshot restore I have actually rehearsed.
