I don’t want a Vault per team.

I want one broker. Hub cluster. Spokes talk to it. Secrets land on paths that identity already decided. That’s the short version of [ADR-0002](https://github.com/ravichandrapatel/idp-gitops-bridge/blob/main/docs/adr/0002-vault-hub.md) in `idp-gitops-bridge` — and the long version lives next to it under `docs/adr/vault/`.

This post is the architecture, the opinions, and a kind lab that actually said “permission denied” until I fixed a dumb ACL detail.

## Why a hub at all

Per-tenant Vault looks tidy on a whiteboard. In production it’s seal keys, Raft disks, audit devices, backup jobs, upgrade weekends — multiplied by every OU that thinks it’s special.

So the decision is blunt:

1. Run a **Vault Hub** (OSS unless you buy Enterprise).
2. Multi-tenancy in OSS = **path convention + policies**. Namespaces and native DR replication stay labeled Enterprise-only in the spec. No pretending.
3. Keep the narrative and Helm overlays under `docs/adr/vault/` with the ADR. One place operators look.

Hub–spoke Argo (ADR-0001) already splits “hub bootstraps, spoke owns day-2.” Vault sits on that same mental model: central security broker, not a pet per cluster.

## Three principles I actually care about

The spec opens with a table. I’ll translate.

**Identity-first.** After login, you’re an Identity Entity with metadata. Not a floating token with a handwritten policy name.

**Policy minimalism.** One “universal” policy template. Not two hundred `payment-api-prod.hcl` files rotting in git.

**Zero-static credentials for clouds/clusters.** Auto-unseal via cloud KMS. Machine auth via JWT / Kubernetes auth or carefully bounded AppRole. Humans via OIDC (Azure AD, Okta — pick your IdP).

If a design violates those three, it’s usually wrong for this IDP.

## The path shape

Metadata keys on the entity:

| Key | Example |
| --- | --- |
| `ou` | `test1` |
| `bu` | `finance` |
| `app_name` | `payment-api` |
| `env` | `prod` |
| `cluster` | `eks-cluster-101` (set at onboarding, not by the pod) |

Secret layout:

```text
{{ou}}-ou/data/{{bu}}/{{app_name}}/{{env}}/*
```

So finance’s payment API in prod reads `test1-ou/data/finance/payment-api/prod/...`. Retail OMS is a different leaf. Same mount. Different metadata. Deny by construction.

KV v2 on every `*-ou` mount. Versioning and metadata API aren’t optional niceties.

## The universal policy

This is the whole joke — one policy, interpolated from identity:

```hcl
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
path "identity/entity/id/{{identity.entity.id}}" {
  capabilities = ["read"]
}
```

Notice the exact leaf **and** the `/*` child. I’ll come back to why that matters.

Hub operators get a separate break-glass policy: auth mounts, entity *aliases*, KV *metadata* — not tenant secret data. If SREs can rewrite `identity/entity/*` metadata, they can impersonate any app. Don’t do that.

## Auth without mount chaos

Don’t create `auth/k8s-<every-cluster-uuid>`. Group by **trust domain**:

- `auth/k8s-prod`
- `auth/k8s-nonprod`
- `auth/k8s-platform`

Bind `iss` (cluster OIDC issuer) and `sub` (namespace:SA) on the role. Same app on EKS and AKS = two roles under `k8s-prod`, different issuers. Cluster claim still lands in metadata for audit.

Toggle the two machine paths. Watch what disappears.

Native Kubernetes / JWT auth is the cleaner machine story. AppRole with `bind_secret_id=false` is in the spec as an option; some reviews call that single-factor. For the kind lab I used AppRole + secret_id because wiring a fake OIDC issuer into kind wasn’t worth the ceremony for a blog screenshot.

## HA, audit, DR — the boring parts that save you

Production shape in the ADR values: Raft ×3 (prefer ×5 for serious), dual disks (data + audit), cloud KMS auto-unseal, LB health only on `/sys/health` **200** (active leader). OSS standbys forward; they don’t serve reads. Performance standby is Enterprise. Plan for that.

Audit: enable immediately after init. Two devices of different types. Vault will stop taking requests if it can’t write audit. That’s a feature until your disk fills.

DR in OSS: Raft snapshots out to object storage, restore with Terraform/automation. Warm standby DR replication = Enterprise. Label it. Don’t hand-wave.

## Kind lab: prove the deny

I stood up `kind` cluster `vault-blog`, Helm chart `hashicorp/vault` in **dev mode** (inmem, single pod, root token). Not production. Not Raft. Fine for proving identity → policy → path.

![kind: vault-0 Running, NodePort services, vault status unsealed](/posts/vault-hub/kind-vault-pods.png)

Entity metadata stamped:

![identity entity metadata ou/bu/app_name/env and universal policy](/posts/vault-hub/identity-and-policy.png)

Then login as the payment-api AppRole:

- `vault kv get test1-ou/finance/payment-api/prod` → `db_password` comes back
- `vault kv get test1-ou/retail/oms/prod` → **403 permission denied**

![ALLOW on own path, DENY on retail/oms](/posts/vault-hub/allow-deny.png)

That’s the architecture in two commands.

### The ACL footgun I hit

First policy only had `.../{{env}}/*`.

Resultant ACL showed a glob under `.../prod/`. Exact path `.../prod` (what `vault kv get` hits for the leaf) was **deny**. Capabilities on `.../prod/db_password` were fine. Wild.

So either grant the exact leaf path, or use a trailing `*` on the leaf segment. The ADR sample in the vault readme still shows the classic `/*` form — treat the exact-leaf grant as a required patch when you copy it. I learned that the hard way on this lab, not from a whitepaper.

Also: create the Identity Entity **with metadata before** the first login. Empty entity + later Terraform “alias already exists” is a miserable afternoon. Spec §4 says this. Believe it.

## What I’d ship next

Trust-domain JWT mounts against a real spoke OIDC issuer. ESO / VSO pulling from the universal path. Snapshot job to S3 that you’ve actually restored once. And a Conftest rule that fails PRs still inventing per-app Vault policies.

One hub. Metadata as tenancy. Policies that don’t multiply.

That’s the architecture.
