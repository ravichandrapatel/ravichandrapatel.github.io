I am currently working on building my own IDP. While debating the architecture I hit a familiar question: where do secrets live?

I went through a lot of documentation and blogs and eventually narrowed it to Vault. I have been using Vault Enterprise across multiple projects for the past five years, so I want to pull those same principles into this IDP setup. Naturally I do not have the budget for an Enterprise license right now, so I am on Vault OSS. I know what is missing compared to Enterprise — namespaces, native DR replication, performance standbys that actually serve reads. Some of that I can approximate. Some of it I cannot. That is fine. I still want the operational shape I am used to.

Went back to the drawing board. During research one gap stood out: almost nobody writes clearly about **how to kill policy sprawl** when you are stuck on OSS and still need multi-tenant isolation.

These notes are my journey building a secure Vault for secrets in my IDP. I know I will not match every Enterprise feature. Below is what I am configuring on OSS, and how I am testing it.

## Decisions

To test the architecture I stood up a kind cluster. I use that cluster for the rest of this write-up.

```bash
export DOCKER_HOST=unix:///var/run/docker.sock   # only if your Docker socket needs it
kind create cluster --name vault-blog --wait 180s
kubectl config use-context kind-vault-blog
```

Once the cluster is up I leave it running in the background. How to deploy Vault on Kubernetes or VMs is already well covered — start with the [HashiCorp Vault on Kubernetes](https://developer.hashicorp.com/vault/docs/platform/k8s) docs and the official Helm chart. I am not repeating a generic install tutorial here. I care about the shape: one hub, many tenants, few policies.

When building an IDP I do not want a separate Vault instance per team. I need a **central Vault** that runs in the Kubernetes cluster where the IDP control plane lives, and application teams (and other clusters / VMs) authenticate into that same broker.

For that I am selecting a **three-node** Vault install. Leader election on integrated Raft storage works on quorum, same mental model as etcd. Quorum wants an **odd** number of voters. Three is the minimum I am willing to call HA. Five if the platform gets serious later.

Once quorum is on the table I need multi-tenant isolation. This Vault will back an IDP — multiple clusters, maybe VMs, many apps. Boundaries first. I am locking these operational principles:

1. **Identity first** — every login lands on an Identity Entity with metadata, not a naked token and a one-off policy name.
2. **Policy minimalism** — one universal policy template driven by that metadata. Not a graveyard of `app-env.hcl` files.
3. **Zero static credentials** in the workloads — short-lived machine auth, cloud KMS auto-unseal, humans on OIDC.

Then the work is mechanical:

- standardize metadata and path schemas
- construct the universal policy
- mandate production infrastructure baselines (Raft, audit, seal, LB health)
- validate login in the lab step by step (with the diagram below)
- write down the footguns so I do not repeat them

## Why a hub (not a Vault per team)

Per-tenant Vault looks tidy on a whiteboard. In production it is seal keys, Raft disks, audit devices, backup jobs, upgrade weekends — multiplied by every OU that thinks it is special. I have lived that on Enterprise. I am not recreating it on OSS for a lab IDP.

So the decision is blunt:

1. One Vault Hub on OSS (Enterprise only if the license shows up later).
2. Multi-tenancy on OSS = **path convention + policies**. Namespaces and native DR replication stay Enterprise — I label that honestly instead of pretending.
3. Same mental model as hub–spoke GitOps: the hub is the broker; spokes and apps come to it.

## Metadata and path schema

Security logic hangs off identity metadata. After auth, Vault stamps the entity:

| Metadata | Example | Notes |
| --- | --- | --- |
| `ou` | `test1` | top-level mount prefix |
| `bu` | `finance` | business unit folder |
| `app_name` | `payment-api` | application id |
| `env` | `prod` | lifecycle |
| `cluster` | `eks-cluster-101` | set at cluster onboarding — not by the pod |

Path layout I am standardizing on:

```text
{{ou}}-ou/data/{{bu}}/{{app_name}}/{{env}}/*
```

So finance / payment-api / prod reads `test1-ou/data/finance/payment-api/prod/...`. A retail OMS leaf is a different path. Same KV v2 mount family. Different metadata. Deny by construction.

I create the Identity Entity **with metadata before** the first login. Empty entity on first auth, then Terraform fighting “alias already exists,” is a day I have already wasted elsewhere. Not again.

## Universal policy

This is the whole point of the research gap I mentioned — stop growing a policy file per app.

```hcl
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
path "identity/entity/id/{{identity.entity.id}}" {
  capabilities = ["read"]
}
```

Notice the exact leaf **and** the `/*` child. OSS KV v2 will surprise you if you only grant the glob — more on that under footguns.

Hub operators get a separate break-glass policy: auth mounts, entity *aliases*, KV *metadata*. Not tenant secret data. If someone can rewrite `identity/entity/*` metadata they can impersonate any app. I am not giving SREs that.

## Production baselines I am mandating

Even on a lab path I am writing the prod rules down so I do not “optimize” them away later:

- Raft integrated storage, **three** nodes minimum (odd quorum)
- Dual disks where I can: data + audit
- Cloud KMS auto-unseal in real environments (dev mode on kind is only for proofs)
- Load balancer / health checks: only `/sys/health` **200** (active leader) gets traffic. OSS standbys forward; they do not serve reads like Enterprise performance standbys
- Audit enabled right after init — ideally two devices of different types. Vault will stop taking requests if it cannot write audit
- OSS DR = Raft snapshots to object storage + a restore path I have actually rehearsed. Warm standby DR replication is Enterprise

## Machine auth — two doors

I am not creating `auth/k8s-<every-cluster-uuid>`. I group by trust domain: `k8s-prod`, `k8s-nonprod`, `k8s-platform`. Roles bind `iss` (cluster issuer) and `sub` (namespace:SA). Same app on EKS and AKS can share the prod mount with different issuers.

## Lab — prove allow and deny

On the kind cluster I installed the official Helm chart in **dev** mode first (inmem, single pod, root token). That is not the three-node prod shape. It is enough to prove identity → universal policy → path isolation before I burn time on Raft in the lab.

![kind: vault-0 up](/posts/vault-hub/kind-vault-pods.png)

![entity metadata + policy](/posts/vault-hub/identity-and-policy.png)

After stamping metadata `ou=test1`, `bu=finance`, `app_name=payment-api`, `env=prod` on the entity and attaching the universal policy:

- `vault kv get test1-ou/finance/payment-api/prod` → secret comes back
- `vault kv get test1-ou/retail/oms/prod` → **403 permission denied**

![allow own path, deny cross-app](/posts/vault-hub/allow-deny.png)

That is the architecture in two commands. Policy sprawl does not get a vote.

## Footguns

**Exact leaf vs `/*`.** A policy that only ends in `.../{{env}}/*` grants paths under `.../prod/`. The exact leaf `.../prod` — what `vault kv get` hits — came back **deny** in my lab. Capabilities on `.../prod/db_password` were fine. Grant the exact leaf path as well, or use a trailing `*` on the leaf segment.

**Bootstrap order.** Entity + metadata + alias before the workload’s first login. Otherwise you fight ghost entities and alias collisions.

**OSS honesty.** Do not document namespaces or DR replication as if they exist on OSS. Path + policy is the tenancy story until a license changes the rules.
