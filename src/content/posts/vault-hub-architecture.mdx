## 1. Intro and Issue

I am currently working on building my own IDP. While debating the architecture I hit a familiar question: where do secrets live?

What I am creating here is not “another Vault tutorial.” I am building a **central Vault Hub** that my IDP control plane and application teams will share — one broker, many tenants — on **Vault OSS**, with isolation that does not depend on Enterprise namespaces. The Hub should answer: can `payment-api` in finance read its own secrets, and can it be hard-denied from touching someone else’s path, without me writing a new policy file for every app?

I went through a lot of documentation and blogs and eventually narrowed it to Vault. I have been using Vault Enterprise across multiple projects for the past five years, so I want to pull those same principles into this IDP setup. Naturally I do not have the budget for an Enterprise license right now, so I am on Vault OSS. I know what is missing compared to Enterprise — namespaces, native DR replication, performance standbys that actually serve reads. Some of that I can approximate. Some of it I cannot. That is fine. I still want the operational shape I am used to.

Went back to the drawing board. During research one gap stood out: almost nobody writes clearly about **how to kill policy sprawl** when you are stuck on OSS and still need multi-tenant isolation.

### The scenario I will use for testing (and keep reusing)

I am thinking of a small but realistic multi-tenant picture for the rest of these notes — and I will use the **same analogy going forward** in the lab, the UI checks, and later when I wire real clusters:

| Piece | What I pretend it is |
| --- | --- |
| Org / OU | `test1` — one customer / org on the Hub |
| Business unit A | `finance` |
| App A (the one I onboard) | `payment-api` in `prod` |
| Business unit B (the neighbor) | `retail` |
| App B (must stay blocked) | `oms` in `prod` |

So: **finance / payment-api** is my happy path. **retail / oms** is the “should get 403” path. Same Vault, same KV mount family (`test1-ou/`), different identity metadata. If payment-api can read retail’s secrets, the design failed.

I am not inventing a second story later for AppRole, UI, or footguns — every command below is proving that one scenario.

These notes walk the problem end to end: what I decided, how I validated it on kind (commands, outputs, and the Vault UI), what broke, and what I would trade off again.

## 2. Architecture and Decision

### Central hub, not a Vault per team

When building an IDP I do not want a separate Vault instance per team. I need a **central Vault** that runs where the IDP control plane lives. Application teams, other clusters, and VMs authenticate into that same broker.

I am selecting a **three-node** Vault for real environments. Raft leader election wants an **odd** quorum (same idea as etcd). Three is the minimum I will call HA. Five later if the platform gets serious.

On OSS, multi-tenant isolation is **path convention + policies**. Namespaces and native DR stay Enterprise — I label that honestly.

![Hub topology — clusters auth in; IdP for humans; short-lived creds out](/posts/vault-hub/architecture.png)

### Principles

1. **Identity first** — login lands on an Identity Entity with metadata.
2. **Policy minimalism** — one universal policy template driven by that metadata.
3. **Zero static credentials** in the workloads — short-lived machine auth, cloud KMS auto-unseal in real clusters, humans on OIDC.

### Metadata and path schema

Using the same test scenario from the intro — this is the identity stamp I put on the `payment-api` entity:

| Metadata | Example | Notes |
| --- | --- | --- |
| `ou` | `test1` | top-level mount prefix (the org in my analogy) |
| `bu` | `finance` | business unit folder |
| `app_name` | `payment-api` | application id |
| `env` | `prod` | lifecycle |
| `cluster` | `eks-cluster-101` | set at onboarding — not by the pod |

```text
{{ou}}-ou/data/{{bu}}/{{app_name}}/{{env}}/*
```

For my scenario that resolves to:

- Allowed: `test1-ou/data/finance/payment-api/prod/...`
- Denied for that same identity: `test1-ou/data/retail/oms/prod/...`

### Universal policy

Exact leaf **and** `/*` — both required (see Issues Encountered).

```hcl
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
path "identity/entity/id/{{identity.entity.id}}" {
  capabilities = ["read"]
}
```

Create the entity **with metadata before** the first login.

### Machine auth

I am not creating one auth mount per cluster. I group by trust domain: `k8s-prod`, `k8s-nonprod`, `k8s-platform`. Roles bind `iss` (cluster issuer) and `sub` (namespace:SA).

## 4. Issues Encountered

**Exact leaf vs `/*`.** A policy that only ends in `.../{{env}}/*` grants under `.../prod/`. The exact leaf `.../prod` (what `vault kv get` hits) came back **403**. Capabilities on `.../prod/db_password` were fine. Fix: grant the exact leaf path as well (or trailing `*` on the leaf). That is why the universal policy has both stanzas.

**Bootstrap order.** If the workload logs in before the Identity Entity has metadata, you get a ghost entity and later “alias already exists” fights with Terraform. Stamp entity + metadata + alias first.

**Root token in the UI.** Works for kind. The UI itself warns that the root token is not stored in the browser. Never use this pattern on a shared cluster.

**Docker socket on WSL.** `kind create` failed until `DOCKER_HOST=unix:///var/run/docker.sock` pointed at the real Docker engine instead of a broken containerd endpoint.

**Port-forward flakiness.** CLI against `127.0.0.1:8200` died when the forward dropped. Running `vault` via `kubectl -n vault exec vault-0 -- ...` was more reliable for the lab script.

**OSS feature honesty.** I kept catching myself writing as if namespaces or warm-standby DR existed. They do not on OSS. Path + policy is the tenancy story until a license changes the rules.

## 5. Pros and Cons

| | Pros | Cons |
| --- | --- | --- |
| **Central Vault Hub** | One seal/backup/upgrade story; teams share a broker | Hub is a shared dependency — plan snapshots and restore |
| **OSS + path tenancy** | No Enterprise license to start; metadata-driven isolation works | No namespaces; no native DR; OSS standbys do not serve reads |
| **Universal policy** | Kills per-app policy files; onboarding is metadata + alias | Templating bugs (exact leaf) are easy to miss; bootstrap order matters |
| **Trust-domain auth mounts** | Few mounts (`k8s-prod` / `nonprod` / `platform`) | Role design must bind `iss`/`sub` carefully |
| **kind + Helm dev mode** | Fast proof of allow/deny and UI | `inmem`, no HA — must not confuse with the Raft values above |
| **AppRole in the lab** | Easy without cluster OIDC | Weaker story than native K8s JWT for real workloads |

## 6. Conclusions

What I set out to create is a **Vault Hub for my IDP**: one OSS broker, tenants isolated by metadata, one universal policy. The **finance / payment-api vs retail / oms** scenario is how I will keep testing that — same analogy when I move from kind to Raft, and when I swap AppRole for real Kubernetes JWT auth.

For my IDP I am staying with that Hub model and a **three-node Raft** shape for anything past the lab. Kind + Helm **dev** mode was enough to prove allow on payment-api and 403 on retail, and to walk the UI. The production values above are what I want next — TLS, dual disks, audit job, snapshot CronJob — once cloud KMS unseal and real storage classes are wired.

Policy sprawl was the research gap that started this. The lab answered it without a graveyard of `app-env.hcl` files.

Next for me: trust-domain JWT against a real spoke OIDC issuer (still as payment-api), External Secrets / VSO on the universal path, and one Raft snapshot restore I have actually rehearsed.
