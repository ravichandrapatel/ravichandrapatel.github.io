## 1. Intro and Issue

When you build an internal developer portal, you hit the same question sooner or later: where do the secrets live?

I'm building a **central Vault Hub** for that portal — one Vault shared by the control plane and app teams, on **Vault OSS**, with tenant separation that doesn't need Enterprise namespaces. Simple test: can one app read only its own secrets, and get denied everywhere else, without me writing a new policy file for every app?

I read a lot of docs and blogs and landed on Vault. I've used Vault Enterprise on projects for about five years, so I want that same way of working here. I don't have money for an Enterprise license right now, so I'm on OSS. OSS doesn't have namespaces, native DR, or standbys that serve reads. Some of that I can fake. Some of it I can't. Fine — I still want the setup I'm used to running.

Went back to the drawing board. One gap kept showing up: almost nobody writes clearly about **how to stop policy sprawl** when you're on OSS and still need multi-tenant isolation.

Let's take a company-style example and keep it for the rest of this note — lab, UI, and later when real clusters show up:

| Piece | Example |
| --- | --- |
| Org / OU | `test1` |
| Business unit (app owner) | `finance` |
| Application | `payment-api` in `prod` |
| Neighbor business unit | `retail` |
| Neighbor application | `oms` in `prod` |

`finance` / `payment-api` should read its own path. That same identity must get **403** on `retail` / `oms`. Same Vault, same mount family (`test1-ou/`), different identity metadata. If payment-api can read retail's secrets, the design failed.

Rest of the note: what I decided, how I proved it on kind, what broke, and what I'd accept again.

## 2. Architecture and Decision

For the portal I don't want a Vault per team. I need a **central Vault** where the control plane lives. App teams, other clusters, and VMs log into that same broker.

I'm picking a **three-node** Vault for real environments. Raft wants an **odd** number of nodes (same idea as etcd). Three is the smallest HA I'll take seriously. Five later if things grow. On OSS, tenant separation is **path layout + policies**. Namespaces and native DR stay Enterprise — I'll say that straight.

![Hub topology — clusters auth in; identity provider for humans; short-lived creds out](/posts/vault-hub/architecture.png)

Three rules for the rest of the design:

1. **Identity first** — login lands on an Identity Entity with metadata.
2. **Few policies** — one shared policy template driven by that metadata.
3. **No static secrets in the apps** — short-lived machine auth, cloud KMS auto-unseal in real clusters, humans on OIDC.

For the company example above, the metadata on `payment-api` looks like this:

| Metadata | Example | Notes |
| --- | --- | --- |
| `ou` | `test1` | top-level mount prefix |
| `bu` | `finance` | business unit folder |
| `app_name` | `payment-api` | application id |
| `env` | `prod` | lifecycle |
| `cluster` | `eks-cluster-101` | set at onboarding — not by the pod |

```text
{{ou}}-ou/data/{{bu}}/{{app_name}}/{{env}}/*
```

That becomes:

- Allowed: `test1-ou/data/finance/payment-api/prod/...`
- Denied for that same identity: `test1-ou/data/retail/oms/prod/...`

One shared policy for every app. You need the exact path **and** the `/*` path — `vault kv get` hits the exact path; nested keys need the wildcard. Skip Issues Encountered and you'll paste a 403 into prod.

```hcl
# Exact path — what `vault kv get .../prod` hits (without this: 403)
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
# Nested keys under that path
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
path "identity/entity/id/{{identity.entity.id}}" {
  capabilities = ["read"]
}
```

Create the entity **with metadata before** the first login.

I'm not creating one auth mount per cluster. I group by trust domain: `k8s-prod`, `k8s-nonprod`, `k8s-platform`. Roles bind `iss` (cluster issuer) and `sub` (namespace:SA). Toggle Native K8s vs AppRole below — watch where trust stops.

## 3. Execution and Validation

To prove the company example, I stood up Vault on kind, wrote a secret under **finance / payment-api / prod**, set identity metadata for that app, checked the read, then checked that **retail / oms** returns 403. Dev mode isn't three-node Raft — it's the fast way to prove the path before I burn time on quorum.

Commands below. I cut the boring success spam. Kept the outputs that matter for the proof.

## 4. Issues Encountered

**Exact path vs `/*`.** A policy that only ends in `.../{{env}}/*` covers things *under* `.../prod/`. The exact path `.../prod` (what `vault kv get` hits) came back **403**. Reads on `.../prod/db_password` were fine. **Fix:** also grant the exact path (or put a trailing `*` on it). That's why the shared policy has both lines.

**Bootstrap order.** If the app logs in before the Identity Entity has metadata, you get a ghost entity and later “alias already exists” fights with Terraform. **Fix:** create entity + metadata + alias *before* the first login.

**Root token in the UI.** Fine for kind. The UI itself warns that the root token isn't stored in the browser. Don't do this on a shared cluster.

**Docker socket on WSL.** `kind create` failed until `DOCKER_HOST=unix:///var/run/docker.sock` pointed at the real Docker engine instead of a broken containerd endpoint.

**Port-forward flakiness.** CLI against `127.0.0.1:8200` died when the forward dropped. Running `vault` via `kubectl -n vault exec vault-0 -- ...` was more solid for the lab script.

**OSS feature honesty.** I kept writing as if namespaces or warm-standby DR existed. They don't on OSS. Path + policy is the tenant story until a license changes that.

## 5. Pros and Cons

| | Pros | Cons |
| --- | --- | --- |
| **Central Vault Hub** | One place to seal, backup, and upgrade; teams share one broker | Hub is a shared dependency — plan snapshots and restore |
| **OSS + path tenants** | No Enterprise license to start; metadata-based isolation works | No namespaces; no native DR; OSS standbys don't serve reads |
| **One shared policy** | No pile of per-app policy files; onboarding is metadata + alias | Easy to miss the exact-path bug; create order matters |
| **Trust-domain auth mounts** | Few mounts (`k8s-prod` / `nonprod` / `platform`) | Role design must bind `iss`/`sub` carefully |
| **kind + Helm dev mode** | Fast allow/deny and UI proof | `inmem`, no HA — don't confuse with the Raft values above |
| **AppRole in the lab** | Easy without cluster OIDC | Weaker than native K8s JWT for real workloads |

## 6. Conclusions

What I set out to build is a **Vault Hub for my internal developer portal**: one OSS broker, tenants split by metadata, one shared policy. I'll keep using the same company example — `finance` / `payment-api` allowed, `retail` / `oms` denied — when I move from kind to Raft and when I swap AppRole for real Kubernetes JWT auth.

I'm sticking with that Hub model and a **three-node Raft** shape for anything past the lab. Kind + Helm **dev** mode was enough to prove allow and deny, and to walk the UI. The production values above are next — TLS, two disks, audit job, snapshot CronJob — once cloud KMS unseal and real storage classes are wired.

Policy sprawl was the research gap that started this. The lab answered it without a pile of `app-env.hcl` files.

Next for me: trust-domain JWT against a real spoke OIDC issuer (still as `payment-api`), External Secrets / VSO on the shared path, and one Raft snapshot restore I've actually practiced.
