Recently I started building an internal developer portal as a side project. When I got to architecture and tool selection, one question kept coming up that I couldn't skip past: what lives where, and who gets to access it. Before I touched implementation, I needed to answer that — everything else in the architecture would end up built around it.

Going back through everything an internal developer portal actually does, the thing I kept landing on first was secrets. Whether the portal ends up single-tenant, multi-tenant, multi-account, or multi-cloud, none of that matters if I haven't figured out how to store secrets securely underneath it. This post is my journey into finding the right answer for my own use case, not a general one. To keep this from becoming a single massive page-long note, I'm splitting it into two parts. This post will be on architecture and decisions behind it. Part 2 will be on deploying this in real/lab clusters to find out if any of this actually works.

## The Tool That Checked Every Box Except the Budget

I looked at a lot of options for storing secrets securely. AWS Secrets Manager was the obvious first stop — easy to use, easy to integrate, secure by default. Azure Key Vault and GCP Secret Manager were both fine candidates too. But I kept coming back to one problem: I need something with no cloud lock-in, so I can bootstrap this IdP on any cloud without rebuilding the secrets layer later.

That one constraint did most of the filtering by itself. No cloud lock-in, works on VMs or containers, can hand secrets to both, supports OIDC-based auth for cloud workloads, gives me real isolation between tenants, and has an HA/DR story I can trust. One more thing, this one about how I wanted to run it, not what the tool could do: one secret broker for all apps, not separate instances per team, tenant, environment, or cloud. That's a short list to write down, but it ruled out almost everything except one tool.

**HashiCorp Vault**. I've been running **Vault Enterprise** at work for the past five years, and it checks every one of those boxes without me having to think twice. There's just one problem: this is a side project, and I don't have an Enterprise budget for it. So my eyes landed on **Vault OSS** instead and I already knew going in that it doesn't give you namespace isolation or the HA story Enterprise does. Those are the things you pay for.

That's the actual fork I was standing at: Enterprise has the isolation model I trust, OSS doesn't, and I can't afford Enterprise. So the rest of this post is me finding out how much of that gap I can actually close on my own and where I hit the point OSS just can't get me there.


## Shape of the Hub

That central-broker requirement becomes a single Vault hub: I run it in the same cluster as my IDP, and every tenant, team, and cloud logs into that same hub.

I already knew this part from my experience running Vault Enterprise and Kubernetes (odd quorum, similar idea as etcd). Taking that into account, 3-node common minimum HA [Raft](https://developer.hashicorp.com/vault/docs/configuration/storage/raft) is what I'm actually running for this, not just a random number I got from the internet.

## How Clusters Actually Onboard

Now that the number of nodes for the Vault hub cluster is sorted, the next question is how a new Kubernetes cluster actually gets onboarded to Vault to fetch secrets. After going through the official documentation, I found three ways of doing this.

1. **Per-cluster mount, TokenReview.** A dedicated Vault auth mount per cluster, and on every login Vault calls back to that specific cluster's Kubernetes API server endpoint to check the token. This is the standard, most-used method.
2. **Per-cluster mount, live OIDC discovery.** A dedicated Vault mount per cluster, but instead of calling the API server, Vault fetches the cluster's signing keys live from its public OIDC discovery endpoint at the moment of login. Because the keys are fetched live, they're automatically rotated at each login. I don't need to manually rotate anything.
3. **One shared mount, static keys.** A single mount holds the public signing keys for every cluster I onboard, copied and pasted in directly, and roles use `bound_issuer` to tell which cluster is trying to log in. This is the only option that reduces mount count — but the con is I have to manually rotate the static keys whenever they change.

Per the design, I chose per-cluster mount with live OIDC discovery. The reason: during an EKS upgrade from 1.20 to 1.21 that I have done, already Vault-onboarded clusters started failing. Going through the documentation, this was Kubernetes' broader move toward OIDC-compliant service account tokens around that version. Service account tokens became short-lived and auto-rotating, and one time the service account used to onboard a cluster got accidentally deleted, which caused a similar issue. Both cases came down to the same root cause: TokenReview depends on a persistent reviewer service account credential that can go stale or get deleted from the cluster. Using OIDC discovery doesn't need those static reviewer tokens — Vault validates against public keys directly — so that entire failure mode goes away. That's the real reason I chose it, not just the automatic rotation.

If you want more on this, HashiCorp's own tracking issue is here: [github.com/hashicorp/vault/issues/11953](https://github.com/hashicorp/vault/issues/11953), and a good practical write-up of the exact 1.21 issue is here: [particule.io/en/blog/vault-1.21](https://particule.io/en/blog/vault-1.21/).

## The shared policy template

To make this concrete, I'll carry one example through the rest of this and part 2 post instead of talking in the abstract about "apps" and "tenants."

Picture the org as it'll actually look once this is live: a top-level org (I'll call it test1), with business units underneath it — say, **finance** and **retail** — and each BU running its own apps. Finance runs something called **payment-api**. Retail runs something called **oms**. Same Vault, same org, two completely different teams who should never see each other's secrets.

If this design works, **payment-api** should read its own secrets without a second thought, and get flatly denied the moment it reaches for anything under retail's **oms** — same policy engine, same Vault instance, nothing but identity telling them apart.


I started with the initial design for app-level isolation: one AppRole and one ACL policy per app, so **payment-api** and **oms** each get their own. In theory, reading the other app's secret returns 403.

On paper it looks good, but doing this for two apps I can manage it. What if I need to onboard multiple applications and multiple organizations? Then the entire day goes into writing the policy.hcl files for each, and I need to spend a night trying to fix where and what is causing the issue. This idea is good when you have a handful of applications and is not the correct architecture path.

That per-app model *is* the sprawl. So: one shared policy template for any secrets path, driven by identity entity metadata. Onboarding becomes assigning attributes, not writing new HCL. The entity carries `<OU>/<BU>/<APP_NAME>/<ENV>`.

Same path shape for both apps: `test1/finance/payment-api/prod` and `test1/retail/oms/prod`. Same template, different metadata, different result.

Below is what I finalized for that template. Prefix naming is `{ou}-ou`, then `{bu}/{app_name}/{env}` (plus `{bu}/shared/{env}`) with cluster authRole. Platform owns new OU/BU prefixes and app teams only store secrets under those approved paths.

**shared/** is BU-wide on purpose, not cross-tenant. Platform jobs that span BUs need their own entity/policy, not a wider universal template.

Metadata-driven policies still need careful review. This hub is a shared dependency. One bad template or wrong metadata attribute can become a cross-tenant leak, or a silent 403 that still looks perfectly valid, across every tenant in that OU/BU.

```hcl
# Exact path: what `vault kv get .../prod` hits (without this: 403)
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
# Nested keys under that path
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
# Intentional: every app in the same BU can read that BU's shared/ path
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
# Self-lookup / debugging; not general app business logic
path "identity/entity/id/{{identity.entity.id}}" {
  capabilities = ["read"]
}
```

Once auth works, the request path is straightforward: the pod presents a Kubernetes JWT, Vault lands on an Identity Entity with metadata, the template expands, and the KV path either allows or returns 403.

The cluster architecture and policy design is ready. Next step is the lab: prove the allow and deny path actually holds with this layout.
