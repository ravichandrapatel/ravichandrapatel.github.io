I am currently working on building my own IDP. While debating the architecture I hit a familiar question: where do secrets live?

I went through a lot of documentation and blogs and eventually narrowed it to Vault. I have been using Vault Enterprise across multiple projects for the past five years, so I want to pull those same principles into this IDP setup. Naturally I do not have the budget for an Enterprise license right now, so I am on Vault OSS. I know what is missing compared to Enterprise — namespaces, native DR replication, performance standbys that actually serve reads. Some of that I can approximate. Some of it I cannot. That is fine. I still want the operational shape I am used to.

Went back to the drawing board. During research one gap stood out: almost nobody writes clearly about **how to kill policy sprawl** when you are stuck on OSS and still need multi-tenant isolation.

These notes are my journey. First the decisions, then how auth is supposed to look, then the kind lab with the commands **and the outputs I got**, including the Vault UI.

## 1. Decisions

When building an IDP I do not want a separate Vault instance per team. I need a **central Vault** that runs where the IDP control plane lives. Application teams, other clusters, and VMs authenticate into that same broker.

I am selecting a **three-node** Vault for real environments. Raft leader election wants an **odd** quorum (same idea as etcd). Three is the minimum I will call HA. Five later if the platform gets serious.

On OSS, multi-tenant isolation is **path convention + policies**. Namespaces and native DR stay Enterprise — I label that honestly.

Operational principles I am locking:

1. **Identity first** — login lands on an Identity Entity with metadata.
2. **Policy minimalism** — one universal policy template driven by that metadata.
3. **Zero static credentials** in the workloads — short-lived machine auth, cloud KMS auto-unseal in real clusters, humans on OIDC.

![Hub topology — clusters auth in; IdP for humans; short-lived creds out](/posts/vault-hub/architecture.png)

## 2. Machine auth — two doors (UI)

I am not creating one auth mount per cluster. I group by trust domain: `k8s-prod`, `k8s-nonprod`, `k8s-platform`. Roles bind `iss` (cluster issuer) and `sub` (namespace:SA).

## 3. Metadata, paths, and the universal policy

After auth, Vault stamps the entity:

| Metadata | Example | Notes |
| --- | --- | --- |
| `ou` | `test1` | top-level mount prefix |
| `bu` | `finance` | business unit folder |
| `app_name` | `payment-api` | application id |
| `env` | `prod` | lifecycle |
| `cluster` | `eks-cluster-101` | set at onboarding — not by the pod |

Path layout:

```text
{{ou}}-ou/data/{{bu}}/{{app_name}}/{{env}}/*
```

Example: `test1-ou/data/finance/payment-api/prod/...`

Universal policy (exact leaf **and** `/*` — that matters):

```hcl
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
path "identity/entity/id/{{identity.entity.id}}" {
  capabilities = ["read"]
}
```

Create the entity **with metadata before** the first login. Empty entity first, then “alias already exists,” is a day I have already wasted.

### 6.3 Write the universal policy

```bash
cat > /tmp/universal.hcl <<'EOF'
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/{{identity.entity.metadata.app_name}}/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}" {
  capabilities = ["read", "list"]
}
path "{{identity.entity.metadata.ou}}-ou/data/{{identity.entity.metadata.bu}}/shared/{{identity.entity.metadata.env}}/*" {
  capabilities = ["read", "list"]
}
path "identity/entity/id/{{identity.entity.id}}" {
  capabilities = ["read"]
}
EOF

vault policy write universal-nested-policy /tmp/universal.hcl
```

Output:

```text
Success! Uploaded policy: universal-nested-policy
```

```bash
vault policy read universal-nested-policy
```

Output: the HCL you just wrote (same paths as section 3).

### 6.5 AppRole login — allow and deny

```bash
vault auth enable approle
```

Output:

```text
Success! Enabled approle auth method at: approle/
```

```bash
vault write auth/approle/role/payment-api \
  token_policies=universal-nested-policy \
  token_ttl=5m token_max_ttl=10m \
  bind_secret_id=true
```

Output:

```text
Success! Data written to: auth/approle/role/payment-api
```

```bash
ENTITY_ID=f03f9620-3fb1-a813-4deb-17726adcf3c2   # from lookup above
ROLE_ID=$(vault read -field=role_id auth/approle/role/payment-api/role-id)
SECRET_ID=$(vault write -f -field=secret_id auth/approle/role/payment-api/secret-id)
MOUNT_ACCESSOR=$(vault auth list -format=json \
  | python3 -c 'import sys,json; print(json.load(sys.stdin)["approle/"]["accessor"])')

echo "ROLE_ID=$ROLE_ID"

vault write identity/entity-alias name="$ROLE_ID" \
  canonical_id="$ENTITY_ID" \
  mount_accessor="$MOUNT_ACCESSOR"
```

Output (example):

```text
ROLE_ID=1968c12e-9aaf-1f57-106e-d1065835bc3d
Key             Value
---             -----
canonical_id    f03f9620-3fb1-a813-4deb-17726adcf3c2
id              c7f2b771-92ca-19b8-8239-a9d23f1d4826
```

```bash
TOKEN=$(vault write -field=token auth/approle/login \
```

## 7. Footguns I hit

**Exact leaf vs `/*`.** A policy that only ends in `.../{{env}}/*` grants under `.../prod/`. The exact leaf `.../prod` (what `vault kv get` hits) came back **403**. Grant the exact leaf as well, or use a trailing `*` on the leaf segment. That is why the HCL above has both path stanzas.

**Bootstrap order.** Entity + metadata + alias before the first login.

**Root in the UI.** Fine for kind. Never for a shared cluster. The UI itself warns you.

**OSS honesty.** Do not document namespaces or DR replication as if they exist on OSS.

## 8. What I want for real (three-node Raft)

When I leave the policy lab, install flips to HA Raft. Overlay sketch from my IDP docs (`idp-gitops-bridge/docs/adr/vault/values.yaml`):

```yaml
server:
  replicas: 3
  ha:
    enabled: true
    raft:
      enabled: true
      setNodeId: true
```

Also: dual disks (data + audit), cloud KMS auto-unseal, LB health only on `/sys/health` **200** (active leader), audit on immediately after init. OSS DR = Raft snapshots + a restore path I have actually rehearsed.
