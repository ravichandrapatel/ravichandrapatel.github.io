## 1. Why GitHub as an IDP

I already spend my day in GitHub. Issues. PRs. Actions. Labels. If the internal developer portal is somewhere else, people stop using it.

So I built a **GitHub-only** control plane: an operator fills an Issue Form, Actions validate and codegen, a GitHub App opens a PR on a private workload repo, and OpenTofu runs there — not on the control plane. No Backstage host for this path. No custom portal UI for v1.

This series is about that path — **IssueOps** for an S3 bucket product — not about writing OpenTofu modules. Modules exist (`gh-platform-modules`, SemVer tags). Part 1 and Part 2 assume a golden path already exists. We talk about intake, authz, uniqueness, PRs, and CI.

**Non-goals for both parts:** authoring module HCL, ClickOps in the AWS console, and treating a public control demo as a multi-tenant SaaS portal.

Live control repo (public demo): [ravichandrapatel/gh-platform-control](https://github.com/ravichandrapatel/gh-platform-control).

## 2. Where the idea came from

I stole the shape (not the code) from Bitovi’s piece *[GitHub as a Platform Engineering Platform — The GitHub Actions Path](https://www.bitovi.com/blog/github-as-a-platform-engineering-platform-the-github-actions-path)*.

Their point: traditional DevOps dumps Helm / Kubernetes / Terraform cognitive load onto every developer. Platform engineering wraps that behind a thinner interface. Bitovi’s GitHub Actions model uses **layers**:

1. **IaC layer** — cloud modules and glue  
2. **Actions layer** — reusable automation catalog (deploy X to Y)  
3. **Deployment layer** — app/workload workflows that call those actions  

I mapped that onto what I already wanted:

| Bitovi idea | My repos |
| --- | --- |
| IaC layer | `gh-platform-modules` (tagged modules — out of scope for this series) |
| Actions layer | `gh-platform-actions` (`tofu-pipeline` pinned by SHA) |
| Deployment / GitOps roots | `infra-dev` / `infra-prod` (private workloads) |
| Intake / catalog / authz | `gh-platform-control` (Issue Forms + `issue-provision`) |

Bitovi talks about “DevOps in a box.” My box is an issue plus labels. Same spirit: hide the machinery, keep Git as the audit trail.

## 3. Four repos, not one mega-IDP

```text
gh-platform-control     → Issue Form, catalog, pins, App PR, tracking Deployments
        ↓ App PR
infra-<env>             → stacks/ + tofu.yml → tofu-pipeline (OIDC to AWS)
        ↑ pin SHA
gh-platform-actions     → validate → plan (+ Conftest) → Environment-gated apply
        ↑ SemVer tag
gh-platform-modules     → golden-path modules (not covered here)
```

Hard rules I stuck to:

- **Environment = AWS account** for the MVP (`dev` / `prod` only).  
- **Control never assumes AWS roles.** OIDC and real GitHub Environments live on `infra-*`.  
- **Actions pinned by commit SHA.** Modules pinned by SemVer tags. No floating `main` / `latest`.

## 4. Developer UX: the Issue Form

Product today: **Provision S3 bucket**. The form is YAML under `.github/ISSUE_TEMPLATE/s3-bucket.yml`. GitHub’s preview looks like this:

![Issue Form preview for Provision S3 bucket — environment, bucket name, project, versioning](/posts/github-idp/issue-form-preview.png)

Fields:

| Field | Role |
| --- | --- |
| Environment | `dev` or `prod` → picks workload repo + account |
| Bucket name | Natural key for uniqueness |
| Project | Tagging |
| Enable versioning | `true` / `false` |

Critical: **`labels: []` on the form.** Opening the form does **not** start provisioning. That is the public-demo gate. Without it, any GitHub user could burn Actions minutes and poke the App on a public control repo.

Trimmed form header (full file in the repo):

```yaml
name: Provision S3 bucket
description: Request an S3 bucket (authorized operators only — public demo is gated).
title: "[provision][s3-bucket] "
labels: []
body:
  - type: markdown
    attributes:
      value: |
        **Public demo gate:** opening this form does **not** start provisioning.
        An authorized operator must label the issue with `issueops` + `product:s3-bucket`
        (and be listed in `config/operators.yaml` or have write access on this repo).
```

Catalog entry (allowlists + natural key — still not “how to write a module”):

```yaml
id: s3-bucket
module:
  path: s3
  ref: s3/v1.0.0
inputs:
  environment:
    required: true
    from_environments: true
  bucket_name:
    required: true
    pattern: "^[a-z0-9][a-z0-9.-]{1,61}[a-z0-9]$"
stack_id_from:
  - product
  - bucket_name
uniqueness_key_from:
  - bucket_name
```

Stack path becomes `stacks/s3-bucket-<bucket_name>/`. Branch `issueops/s3-bucket-<bucket_name>`. No issue number in the path — Git is the uniqueness source of truth.

## 5. Public gate and authz

Defense in depth for a **public** control repo:

1. Form does not auto-apply `issueops` / `product:*`.  
2. Workflow `if:` requires those labels before any job runs.  
3. `scripts/authorize_requester.py` fails closed unless the **issue author** is in `operators.yaml` **or** has write/maintain/admin on control.  
4. Workloads stay private.

```yaml
# config/operators.yaml
operators:
  - ravichandrapatel
```

Workflow gate (concept):

```yaml
on:
  issues:
    types: [opened, edited, reopened, labeled]

jobs:
  provision:
    if: >-
      contains(github.event.issue.labels.*.name, 'issueops') &&
      contains(github.event.issue.labels.*.name, 'product:s3-bucket')
```

## 6. Labels as state

| Label | Meaning |
| --- | --- |
| `issueops` | This issue is intake |
| `product:s3-bucket` | Product router |
| `status:pending-validation` | Waiting on control |
| `status:pr-open` | Workload PR exists |
| `status:validation-failed` | Catalog / duplicate / schema rejected |
| `status:plan-ok` / `plan-failed` | From workload `status-sync` |
| `status:applied` / `apply-failed` | From workload `status-sync` |
